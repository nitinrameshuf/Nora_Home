First install, on the Pi

One script takes a bare Raspberry Pi 5 to a running house: Docker, the repo, both HDMI displays in kiosk mode, and a service that starts the house on boot. 

# on the Pi itself, from a clone of the repo
git clone <your git url> ~/nora-home
cd ~/nora-home
./nora install

Everything is ./nora. One command runs the house: installing, starting, updating, backups, apps, and both screens. Run ./nora help at any point to see the whole list — it is the one piece of documentation guaranteed to be in front of you when you need it.

Optional, run first if you don't want to be asked for your password partway through:

sudo ./scripts/lib/pre-provision-pi.sh

Installing into a folder other than ~/nora-home? Set NORA_HOME_DIR to it, or the install tries to clone a second copy beside it and stops, asking for a NORA_HOME_REPO it does not need.

If Docker was already installed before you ran the script, your user may not be in the docker group yet, and the build will fail with permission denied … docker.sock. Fix once:

sudo usermod -aG docker $USER
newgrp docker   # applies it to this shell immediately, no logout needed

What ./nora install does, in order:

1. Packages

Docker (if missing), git, make, Chromium, and the kiosk helper tools.

2. The repo & .env

Clones if needed, creates .env with a fresh secret key and Pi-specific settings.

3. TLS cert

Generates the self-signed cert nginx uses to serve the house over HTTPS — see below.

4. The stack

docker compose up -d --build — first run builds images, ~10 minutes.

5. Start on boot

Installs a systemd unit so the house comes back up after a power cut.

6. Both displays

HDMI-0 (24" wall) and HDMI-1 (10.1" kiosk) each auto-start Chromium in kiosk mode, pointed at the right URL.

Once it finishes:

cd ~/nora-home && ./nora member <you> admin   # create your login
# sign in once on the wall and kiosk screens — they stay signed in
sudo reboot                                     # both screens come up on their own

Accessing the house securely (HTTPS)

The house is reachable on port 443 (regular HTTPS — the same port every other site on the internet uses), not the old :8000. Plain HTTP on port 80 still works, but only to redirect to HTTPS automatically. 

https://<the Pi's address>/home/

Your browser will warn you once per device. This house has no public domain name — it's a Raspberry Pi on your own LAN — so there's no certificate authority that could ever issue it a certificate a browser already trusts. The install generates its own ("self-signed") cert instead. It still fully encrypts the connection; the warning just means your browser can't independently vouch for who's on the other end, which on a device you're looking at directly, on your own network, is fine.

Click Advanced (Chrome, Edge) or Advanced… → Accept the Risk and Continue (Firefox), then proceed. Each browser on each device only asks this once.

The wall and kiosk screens never see this warning at all — Chromium is launched in kiosk mode with the warning suppressed automatically, since nothing is there to click it on an unattended boot.

If the Pi's address on your network ever changes

The cert is generated once, during install, and bakes in whatever LAN IP the Pi had at that moment. If the Pi later gets a different IP (a router reset, a new DHCP lease), the cert still works — the connection is still encrypted — but your browser will flag the mismatch as a second, separate warning to click through. To make it match again: delete the two files in nginx/certs/ on the Pi and run ./nora cert, which regenerates it and reloads nginx.

Updating the house

From here on, every update to the platform itself is one command.

cd ~/nora-home && ./nora upgrade

What ./nora upgrade actually runs

A backup first, then git pull --ff-only → docker compose build → migrate → docker compose up -d. Migrations run here rather than only on container start, so a failed migration stops the upgrade instead of leaving a half-started house. Your data lives in Docker's own volumes (MariaDB, Mongo, MinIO), which none of this touches.

The one that catches people: if you edit .env, a restart will not pick up the change. A running container keeps the environment it started with, so the container has to be replaced:

./nora recreate

Everyday commands

CommandDoes
./nora statusWhat is running, plus a health check
./nora logsFollow the logs
./nora restartRestart the app, leaving the databases alone
./nora recreateReplace containers after editing .env
./nora upgradeThe routine update
./nora backupTake a full backup right now
./nora restore <file>Restore one (asks first)
./nora screensReload the wall and kiosk after a change
./nora member <name>Add someone to the household
./nora uninstallRemove the house, backing up first (asks first)
./nora helpAll of it

Installing a house app

A family member writes an app (see docs/Main_App/DEVELOPMENT.md), then it gets installed once: 

make app SRC=https://github.com/you/nora-workout
# or, for something already sitting in houseapps/ locally:
python manage.py install_app houseapps.workout

This does five things, and the last one is the one people don't expect:

  1. Clones or copies the app into houseapps/<name>
  2. Checks it actually declares itself as a Nora Home app
  3. Registers it in .env so the platform loads it
  4. Generates and applies its database migrations
  5. Commits the app into this platform repo's own git history

Why the commit matters. Without it, an installed app is just loose files sitting on one Pi's disk — invisible to git status, not included in a fresh clone, gone the moment the SD card dies. Committing it is what makes the app part of the house's permanent record, the same as any platform code.

Uninstalling a house app

There are three levels, from safest to most permanent. The command is the same; the flags decide how much you're actually removing.

CommandNav entryApp codeDatabase rowsWhen to use it
uninstall_app workout removedkeptkept Pausing an app. Reinstalling brings it back exactly as it was.
uninstall_app workout --purge-data --yes removedkeptdropped Starting that app over from a clean slate, keeping the code.
uninstall_app workout --remove-files --yes removeddeletedkept Moving the app elsewhere; data waits to be re-registered against.
both flags together, --yes removeddeleteddropped Actually done with the app. Full removal.

make uninstall NAME=workout runs the safe, default form.

--purge-data and --remove-files both refuse to run without --yes. They are real, immediate data loss — there is no undo beyond restoring a backup.

What happens to your data — the full picture

The single question worth answering clearly: which of these operations can lose data, and which can't.

OperationYour dataWhy
make deploy (routine update) Safe Data lives in Docker volumes, untouched by a git pull or an image rebuild. Migrations only ever add.
install_app (new app) Safe Purely additive — new tables, new nav entry, nothing existing is touched.
uninstall_app (no flags) Safe Only edits .env. Code and tables are untouched.
uninstall_app --purge-data Destructive Drops that app's tables on purpose. Everything else in the house is unaffected.
uninstall_app --remove-files Code only Deletes the app's source, not its data — rows sit orphaned until the app is reinstalled or purged.
Fresh git clone instead of reusing the existing checkout Risky Any house app installed on the old checkout is committed to that checkout's git history. A brand new clone from the same remote will still have it, as long as it was pushed — but a clone made before pushing, or from a different remote, will not.
SD card failure / lost Pi Depends on backups See Backups and restore below — this is the one scenario version control alone doesn't cover.
docker compose down -v Destructive The -v deletes the volumes themselves. Nothing in this guide's normal commands does this — it would have to be typed by hand.

Backups and restore

The one thing git doesn't cover is the SD card itself dying. That's what backups are for. 

make backup                              # SQL + Mongo + media + a portable fixture dump, right now
make restore FROM=/var/backups/nora/nora-....tar.gz

What a backup actually contains

A SQL dump (fast, exact restore to the same engine), a Mongo archive, copied media files, and a portable JSON fixture of the entire ORM — the fixture is what lets you restore onto a different database engine entirely, which is the escape hatch for moving off this Pi someday.

Status: written, not yet run against real infrastructure. Backup and restore have been reviewed but never executed against a live MySQL/Mongo stack — see the story dashboard for current status before relying on this as your only safety net.

Troubleshooting real snags

Two things that actually happened on the first real Pi install, kept here so the next person doesn't lose an afternoon to them.

docker: permission denied while trying to connect to the docker API

Your user isn't in the docker group yet — this happens when Docker was already installed before the install script ran, so it skipped the step that adds you.

sudo usermod -aG docker $USER
newgrp docker   # picks it up immediately, no logout required
Image build fails on "apt-get install mongodb-database-tools"

mongodb-database-tools is not a Debian package — it only exists in MongoDB's own apt repository, so this always failed on stock Debian or Raspberry Pi OS. Fixed in the Dockerfile: the platform's own backup/restore commands already skip Mongo tooling gracefully when it's absent, so the house runs fine without it. If you're on a version of this repo from before that fix, pull the latest before building.
